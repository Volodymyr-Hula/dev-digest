## 1. Frontmatter, size limits, structure, progressive disclosure (official)

### Takeaway
Only `description` (plus name) sits in context until the skill triggers; the body loads on use and stays in context. Keep SKILL.md under 500 lines and push bulk into one-level-deep reference files that SKILL.md says when to open. Frontmatter fields are mostly optional in Claude Code.

### Cited Findings
- Claude Code frontmatter: all fields optional, `description` recommended; unknown fields ignored. Fields: `name` (defaults to dir name), `description`, `when_to_use` (appended to description), `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context` (`fork`), `agent`, `background`, `hooks`, `paths` (glob patterns that activate the skill), `shell`, and informational `metadata`/`license`/`compatibility` — [Claude Code skills](https://code.claude.com/docs/en/skills)
- `allowed-tools` pre-approves tools for the invoking turn only and does not restrict other tools; `disallowed-tools` removes tools while the skill is active — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Listing cap: combined `description` + `when_to_use` truncated at 1,536 characters in the skill listing; put the key use case first — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Platform API/base-spec constraints: `name` max 64 chars, lowercase letters/digits/hyphens, no XML tags, reserved words `anthropic`/`claude` banned; `description` non-empty, max 1,024 chars, no XML tags — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); same 1024 limit in [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions). (Claude Code's 1,536 listing cap vs 1,024 spec limit differ; keeping under 1,024 satisfies both.)
- "Keep SKILL.md under 500 lines"; split into separate files when approaching it — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [Claude Code skills](https://code.claude.com/docs/en/skills). agentskills.io additionally recommends under ~5,000 tokens — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Three-level progressive disclosure: metadata, SKILL.md body, linked files read only when needed — [Anthropic engineering blog](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Keep references one level deep from SKILL.md (nested refs lead Claude to partial reads such as `head -100`); give reference files >100 lines a table of contents; name files descriptively (`reference/finance.md`, not `doc2.md`) — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Tell the agent WHEN to load each file ("Read references/api-errors.md if the API returns non-200") rather than generic "see references/" — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Naming: gerund form recommended (`processing-pdfs`), noun phrases acceptable; avoid vague (`helper`, `utils`); keep consistent across the collection — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Locations: project `.claude/skills/<name>/SKILL.md`; personal `~/.claude/skills/`; nested `<subdir>/.claude/skills/` loads when Claude first reads/edits a file in that subdirectory; live change detection, `/reload-skills` if missing — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Invocation control: default = user and Claude can invoke, description always in context; `disable-model-invocation: true` = user only, nothing in context until invoked; `user-invocable: false` = Claude only — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Lifecycle: invoked skill content persists in conversation; after compaction each skill keeps its first 5,000 tokens, all re-attached skills share 25,000 tokens — [Claude Code skills](https://code.claude.com/docs/en/skills). (Implication: put the hard rules at the top of SKILL.md.)
- Skill `paths` field: "Glob patterns that activate the skill" — [Claude Code skills](https://code.claude.com/docs/en/skills). Exact semantics (auto-load vs. limit visibility) were in the truncated part of the page; not verified.

### Inferences
- For an architecture-rules skill: SKILL.md = layer map, dependency rules, top gotchas, self-check checklist (<~200-300 lines); `references/` = per-layer detail, code templates, migration/exception notes, each linked directly from SKILL.md with a "read when…" trigger.
- Because only the first 5,000 tokens survive compaction, front-load the non-negotiable rules.

### Gaps
- Exact `paths` semantics for skills not read (page truncated at char 100,000).
- Did not read the agentskills.io specification or anthropics/skills skill-creator source.

## 2. Authoring best practices: conciseness, freedom, descriptions, style, evaluation

### Takeaway
Add only what Claude would get wrong without you (project-specific conventions, gotchas), write the description as "what + when" in third person, calibrate prescriptiveness to fragility (architecture boundaries are fragile, so be low-freedom there but explain why), and iterate against real runs and trigger evals.

### Cited Findings
- Conciseness: "The context window is a public good"; challenge each paragraph ("Does Claude really need this explanation?"). Cut anything the agent would get right anyway — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Degrees of freedom: high freedom (text heuristics) when many approaches valid; medium (templates/pseudocode); low (exact scripts, "do not modify") for fragile operations — narrow-bridge analogy — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Explaining why helps for flexible instructions: "an agent that understands the purpose behind an instruction makes better context-dependent decisions" — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Descriptions: always third person (injected into system prompt; mixed POV hurts discovery); include what it does AND when to use it, with specific key terms; avoid "Helps with documents" — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Descriptions, agentskills.io view: use imperative phrasing ("Use this skill when…"), focus on user intent not implementation, "err on the side of being pushy" by listing contexts including ones where the user doesn't name the domain — [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions). (Note tension: Anthropic best-practices says third person; agentskills.io says imperative "Use this skill when…". Both examples in Anthropic docs use "Extracts … Use when …" hybrid.)
- Agents typically consult skills only for tasks needing knowledge beyond what they can do alone; simple one-step requests may not trigger even with a matching description — [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)
- Claude Code: "If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help. To tell Claude to use a specific skill, invoke it with /<name>" — [Extend Claude Code](https://code.claude.com/docs/en/features-overview). Also: too much loaded context means "skills may not trigger correctly, or Claude may lose track of your conventions" — same source.
- Skill design scope: treat a skill like a function — coherent unit; too narrow forces multiple skills to load, too broad hard to trigger — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Gotchas section is "the highest-value content in many skills"; keep gotchas in SKILL.md, not a reference file (agent may not recognize the trigger to open it); add every correction you have to make to it — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Favor procedures over declarations; provide defaults, not menus; consistent terminology (one term per concept); avoid time-sensitive info (use an "old patterns" section) — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Examples: input/output pairs convey style better than prose; templates for strict output formats; checklists (copyable progress list) for multi-step workflows prevent skipped steps — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Feedback/validation loops: do work, run validator, fix, repeat; "Only proceed when validation passes". A reference doc can serve as the validator for non-code skills. Make validator error messages specific — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Stronger wording as an iteration fix: observed that a rule was missed, recommended making it more prominent, "MUST filter" instead of "always filter" — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Evaluation-driven development: run Claude without the skill on representative tasks, note failures, build ≥3 evals, write minimal instructions to close gaps, compare to baseline; test with Haiku, Sonnet and Opus; "Claude A writes, Claude B tests" iteration; watch how Claude navigates (ignored files, missed links) — [Best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Ground skills in real project material (code review comments, VCS history, failure cases), not generic LLM knowledge; read execution traces — [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)
- Trigger evals: ~20 queries (8-10 should / 8-10 should-not, with near-misses), 3 runs each, trigger rate threshold 0.5, 60/40 train/validation split, ~5 iterations; skill-creator automates it — [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)
- Skill-writing approach from Anthropic: pay special attention to name and description; have Claude record successful approaches and mistakes into the skill — [Anthropic engineering blog](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Community claims (unverified, no primary source): directive "ALWAYS invoke when…" descriptions improve triggering; silent description-budget overflow can drop skills; a UserPromptSubmit hook can force activation — [DEV Community 1](https://dev.to/lizechengnet/why-claude-code-skills-dont-trigger-and-how-to-fix-them-in-2026-o7h), [DEV Community 2](https://dev.to/oluwawunmiadesewa/claude-code-skills-not-triggering-2-fixes-for-100-activation-3b57) (seen only via search snippets/summary, not fetched)

### Inferences
- Architecture-skill description pattern: "<What: layer rules for server/ onion architecture>. Use when adding or modifying routes, services, repositories, domain entities, or imports across layers in server/, even if the user does not mention 'architecture'." Keep <1,024 chars, key triggers first.
- Rule style that sticks: imperative, each rule with a one-line "why", a wrong/right code pair (negative example) for the 3-5 most commonly violated rules, a "Gotchas" section inline, and a final self-check checklist with runnable commands (typecheck, a grep/dependency-cruiser style import check).
- For an "instruction"-type (reference) skill, since Claude reads it only when triggered, a hook or CLAUDE.md pointer is needed to guarantee it is consulted (see section 3).

### Gaps
- No quantitative data from Anthropic on trigger reliability; the claude.com blog says it does not quantify it.
- No published official guidance specific to encoding architecture rules; recommendations above are inferred from generic guidance.

## 3. Skill vs CLAUDE.md vs path-scoped rule vs hook/linter

### Takeaway
CLAUDE.md, rules and skills are all advisory context ("not enforced configuration"); only hooks, permissions/managed settings (and by extension linters/tests in CI) are deterministic. Use CLAUDE.md for always-true short facts, `.claude/rules/` with `paths:` for file-scoped constraints, skills for on-demand procedures/reference, and hooks for must-hold guardrails.

### Cited Findings
- "Claude treats CLAUDE.md files and auto memory as context. They aren't enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead"; specificity and concision improve adherence — [Memory docs](https://code.claude.com/docs/en/memory)
- CLAUDE.md is delivered as a user message after the system prompt; "no guarantee of strict compliance, especially for vague or conflicting instructions" — [Memory docs](https://code.claude.com/docs/en/memory)
- CLAUDE.md guidance: target under 200 lines per file; longer reduces adherence; write verifiable instructions ("API handlers live in src/api/handlers/"); contradictions cause arbitrary picks; `@imports` do not reduce context cost — [Memory docs](https://code.claude.com/docs/en/memory)
- "If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule" — [Memory docs](https://code.claude.com/docs/en/memory)
- `.claude/rules/*.md`: discovered recursively; rules without `paths` load at launch with same priority as `.claude/CLAUDE.md`; with `paths:` YAML list of globs (e.g. `"src/api/**/*.ts"`) they load when Claude Read/Write/Edits a matching file (or reads one via cat/head); path-scoped rules not matched since compaction are re-loaded on demand; user-level rules in `~/.claude/rules/` — [Memory docs](https://code.claude.com/docs/en/memory)
- Rules vs skills: "Rules load into context every session or when matching files are opened. For task-specific instructions that don't need to be in context all the time, use skills" — [Memory docs](https://code.claude.com/docs/en/memory). Unscoped rules cost the same as CLAUDE.md — [Claude blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Comparison table: CLAUDE.md loads every session; rules every session or on matching files; skills on demand when invoked or relevant. Skills' context cost is low (descriptions every request) — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Hook vs skill: hooks fire deterministically and cost zero context unless they return output; "An instruction like 'never edit .env' in CLAUDE.md or a skill is a request, not a guarantee... If a rule must hold every time, make it a hook." Pairing: PostToolUse hook runs linter and sends errors to Claude; a skill (`/fix-lint`) teaches how to fix — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Hook mechanics: PreToolUse can block; exit 2 blocks and stderr is fed to Claude as feedback; exit 0 does not approve; example blocks Edit/Write to protected files by pattern; hooks can be prompt-type or agent-type for judgment-based checks; `permissions.deny` (e.g. `Edit(/.env)`) also blocks shell-edit paths — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Settings rules are enforced by the client; CLAUDE.md is "not a hard enforcement layer" — [Memory docs](https://code.claude.com/docs/en/memory)
- Anthropic's trigger table: "Claude gets a convention or command wrong twice → add to CLAUDE.md"; "paste the same playbook for the third time → skill"; "something to happen every time → hook" — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Claude blog: skills for repeatable procedures; "A real guardrail needs to be deterministic, and the enforcement methods are hooks and permissions"; Claude "will follow the instruction most of the time" — [Claude blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- `InstructionsLoaded` hook can log which CLAUDE.md/rules load and when — useful for debugging path-scoped rules — [Memory docs](https://code.claude.com/docs/en/memory)
- Skills are meant to combine with CLAUDE.md: "CLAUDE.md says 'follow our API conventions,' a skill contains the full API style guide" — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)

### Inferences
- Layered recommendation for onion architecture: (a) CLAUDE.md: 3-6 lines stating the layer map and dependency direction plus a pointer "before editing server/src, load the `<arch>` skill" (the project's existing CLAUDE.md already follows the "pointers" style); (b) `.claude/rules/<x>.md` with `paths: server/src/domain/**` etc. for short per-layer prohibitions (e.g., "domain imports nothing from infra") that auto-load exactly when those files are touched — more reliable than waiting for description matching; (c) skill for the full how-to (adding a use case/repository end to end, templates, gotchas, self-check); (d) hard enforcement of import direction via a linter/test (dependency-cruiser, eslint boundaries, or a vitest import test) run in CI and optionally a PostToolUse hook that runs it and feeds failures back (exit 2). The dependency-direction rule is deterministic and checkable, so it should not rely on prose alone.
- Path-scoped rule vs skill choice: if the rule is short and tied to file locations, use a rule; if it is a procedure or a long catalog with examples, use a skill.
